You arrive as a transfer student at Hanamori High. You discover that the school has a legend: when the Seventh Name is spoken, a student dies.

The disturbing part is that the school has forgotten the student who originally died. Records contradict one another, NPCs remember different versions of events, and even the school archive has been corrupted.

Your job is not simply to ask an AI questions until it tells you the answer. Your job is to collect evidence, identify contradictions, reconstruct the true timeline, and perform the correct ritual before the loop ends.

The game has three intertwined systems:

- Mystery system: find the truth hidden in documents and conversations.
- Time-loop system: manage Action Points (AP) and learn across repeated attempts.
- Corruption system: watch the fictional repository deteriorate as the curse progresses.

The third system is an additional game mechanic from your second document, not a replacement for the first two.

## 1.2 One complete playthrough

Here is how a single loop should feel to the player.

Phase 1 — The arrival

Start of loop · 8 AP

The game introduces the school, the curse, and the available actions. The player sees their notebook, remaining AP, suspects, archive, and corruption panel.

Phase 2 — Investigate

Spend AP to gather evidence

The player searches an archive, questions a suspect, or cross-checks two records. The engine returns information, unlocks any associated clues, and updates the notebook. The local LLM narrates the discovery.

Phase 3 — The curse reacts

After costly or incorrect actions

The fictional Git repository changes. Commit messages become suspicious, files disappear, or the corruption indicator increases. The player sees that the curse is damaging the evidence itself.

Phase 4 — Form a theory

The notebook preserves discovered clues

The player connects dates, statements, and inconsistencies. They may consult another NPC or use the remaining AP to check a theory.

Phase 5 — The Okuribi ritual

The player chooses the identity of the true dead student and an offering. The engine checks both against the designed solution.

- Correct: the curse breaks and the ending plays.
- Incorrect: the calling claims another student; the loop resets, with persistent clues and consequences.

Important design decision: the ritual should be available before AP reaches zero. If the player uses every AP point, the calling triggers automatically. This makes the ritual a strategic choice rather than merely a final screen.

Also, a failed action should not automatically mean a wrong answer. An invalid input, a failed search, a contradiction, and an incorrect ritual are different events and should have explicitly defined costs.

# 2. How the game architecture actually works

You already know about RAG, MCP servers, and the distinction between truth and corrupted records. The missing piece is how they interact during a turn.

## 2.1 The full architecture

Streamlit UI

Player actions · dialogue · AP · notebook · corruption panel

LangGraph Director

Validate action → route → execute → update state → select next phase

Local LLMs

Intent, dialogue, narration

Game engine

Truth, AP, clues, verdict

Archive MCP

Search and retrieve records

Timeline MCP

Dates and consistency checks

Cursed-repo MCP

Safe fictional corruption

Persistence

Checkpoints and notebook

Conceptual architecture. MCP tools are called by the game workflow where appropriate; they do not all need to be invoked on every turn.

The Director is the central coordinator. It receives the player's action and decides which operation runs. The LLM is one component within that workflow, not the authority over the entire world.

### Example: one archive-search turn

Suppose the player chooses to investigate the student council records.

1. UI: submits `search_archive` with the player's query.
2. Director: validates that the game is active and the player has at least one AP.
3. Router: identifies the action. If the player used free text, a local model may classify it into a structured action.
4. Archive service: retrieves the relevant documents, including metadata such as date, author, reliability, and forged status.
5. Clue checker: compares the retrieved document IDs with your predefined clue mapping. It unlocks only clues earned by that action.
6. State updater: deducts AP and updates the notebook and corruption level according to the game rules.
7. Narrator LLM: turns the retrieved information into a short atmospheric description, using only the permitted evidence.
8. UI: displays the narrative, remaining AP, newly discovered clues, and repository changes.

The next action begins only after the current turn is resolved.

This ordering matters. If you ask an LLM to determine whether the player found a clue, it might unlock the wrong clue or invent one. The game engine must make that decision.

## 2.2 What is Truth RAG versus Corrupt RAG?

Think of these as three separate layers, rather than two interchangeable knowledge bases.

| Layer           | Contents                                                                           | Who can access it?                                      |
| --------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Ground truth    | Actual death, genuine timeline, forged records, NPC secrets, correct ritual answer | Game engine and authorized internal logic               |
| Archive corpus  | Diaries, school records, newspapers, conflicting testimony, false leads            | Archive retrieval tools and the player-facing narrative |
| Player notebook | Clues the player has actually discovered and theories they have formed             | Player and relevant game logic                          |

The distinction is important: a forged document is not necessarily a corrupted retrieval result. It is an intentionally false artifact in the fictional world. RAG retrieves that artifact faithfully; the mystery is figuring out whether it is trustworthy.

For example:

- Ground truth: Student A died during the festival.
- Record D04: claims Student A transferred schools in June.
- Record D11: records Student A attending a club meeting in September.
- Record D18: a forged document created to hide the original death.

The player retrieves these records and discovers contradictions. The model can describe the contradiction, but it must not decide that Student A is the ghost simply because the records look suspicious.

You can implement the archive with Chroma or FAISS and an embedding model via Ollama. Start with a simple Python retrieval function before adding vector search. For a small corpus of approximately 25 documents, basic search may already be sufficient for the first playable version.

## 3.1 Use different contexts for different jobs

I recommend three logical roles. You don't need three simultaneously loaded models.

Role A — Intent router

Small model · E2B

Converts free-text input into structured actions, such as `search_archive`, `talk_to_npc`, `cross_check`, or `perform_ritual`.

Context: allowed action names, valid parameters, current phase, and the player's latest request. No full lore or NPC conversation history is necessary.

Role B — NPC dialogue

Dialogue model · E4B

Speaks as a specific suspect, reacts to the player's question, and expresses uncertainty, fear, or suspicion.

Context: NPC persona, allowed facts, facts already revealed, relevant retrieved evidence, recent dialogue, and the current situation.

Role C — Narrator

Dialogue model · E4B

Writes atmospheric descriptions for discoveries, consequences, transitions, and endings.

Context: the current event, relevant evidence, mood, location, and what the player is permitted to know. It does not need the full world bible.

For a CPU-only machine with 16 GB RAM, start by keeping only one generation model loaded at a time. Measure latency and memory consumption before deciding whether the additional model roles are worth maintaining. You can even begin with a single model and three different prompts.

Also, do not send every document and the complete game history to every call. Context selection should be deliberate.

## 3.2 Example: what an NPC's actual context might look like

Suppose the player asks a student council member:

> Why does the newspaper say the festival was held on September 18 when the club log says September 21?

Your dialogue node could construct a context like this:

```
npc_context = {    "npc_id": "student_council_president",    "persona": {        "name": "Mizuki",        "traits": ["composed", "defensive", "observant"],        "speech_style": "short, guarded responses",    },    "allowed_facts": [        "The festival was planned for September 21.",        "The newspaper was published on September 18.",    ],    "revealed_facts": [],    "evidence": [        {            "id": "D04",            "text": "The newspaper announces the festival.",            "reliability": "questionable",        },        {            "id": "D11",            "text": "The club log records preparations on September 21.",            "reliability": "moderate",        },    ],    "player_question": (        "Why do the newspaper and club log have "        "different dates?"    ),    "recent_dialogue": [],}
```

The LLM then receives a system instruction that it must stay within Mizuki's authorized knowledge, not invent historical facts, and return a short response.

For example, it might say:

> "The newspaper was printed early. That doesn't mean the festival happened that day. Why are you looking so closely at the dates?"

That is a plausible character response, not a guaranteed exact model output.

Notice what is missing from the context:

- The complete `truth.json`.
- Other NPCs' private secrets.
- Every document in the archive.
- The correct answer to the ritual.

Those omissions are intentional.

### A crucial detail: prompts are not security boundaries

If you put the full solution into a prompt and tell the model not to reveal it, a model can still reveal it accidentally. The safer architecture is to avoid supplying unauthorized secrets in the first place.

Even `allowed_facts` is not enough on its own. You should also control which tools an NPC can call, which evidence reaches the dialogue node, and which facts the output validator permits it to state.

## 3.3 What persists between turns and between loops?

Your project needs three distinct kinds of state.

1\. Turn state

Exists during the current action.

Current request, retrieved documents, generated dialogue, candidate clue IDs, and the result of the current action.

2\. Loop state

Resets when a loop ends.

AP remaining, NPC conversations, temporary reveals, the current phase, and the events that occurred during this attempt.

3\. Persistent player state

Survives a loop reset.

Notebook clues, established deductions, loop number, and any intended persistent consequences or déjà-vu traces.

Implement these explicitly in your `GameState` and persistence design.

LangGraph's checkpointer is useful for saving and resuming execution, but a checkpoint is not automatically a new game loop. You must define which fields reset, which survive, and how a new loop is initialized. A persistent Store can hold cross-loop data, while a new thread or a deliberate state transition can represent the next attempt.

For a single-player prototype, you can begin with SQLite-backed checkpoints and a simple notebook store. You do not need a distributed database.

## 3.4 How do MCP servers fit into this?

MCP is the tool-access layer. It is not the game engine, the LLM, or the retrieval algorithm itself.

| MCP tool           | Example operation                                 | Game-engine responsibility                                       |
| ------------------ | ------------------------------------------------- | ---------------------------------------------------------------- |
| Archive server     | Search or retrieve document D11                   | Validate AP and unlock earned clues                              |
| Timeline server    | Compare dates or check chronology                 | Interpret the result under predefined game rules                 |
| Cursed-repo server | Read corruption status or apply a corruption step | Decide when corruption should happen and which event triggers it |

One implementation detail worth preserving: a deterministic timeline check can be a plain Python function at first. Expose it through MCP when you need a separate tool boundary, want to demonstrate MCP, or want the Director to invoke it through the common tool interface.

Similarly, the archive's internal search function can be tested independently of its MCP server.

This is how you avoid turning every component into an AI agent when ordinary code is more reliable.

## Concepts to learn in more depth

### A. Finite-state machines before LangGraph

Your game has explicit phases:

```
class GamePhase(str, Enum):    INTRO = "intro"    INVESTIGATION = "investigation"    RITUAL = "ritual"    CALLING = "calling"    ENDING = "ending"
```

Then define the allowed transitions:

- `INTRO → INVESTIGATION`
- `INVESTIGATION → INVESTIGATION`
- `INVESTIGATION → RITUAL`
- `INVESTIGATION → CALLING` when AP reaches zero
- `RITUAL → ENDING` when the answer is correct
- `RITUAL → CALLING` when the answer is wrong
- `CALLING → INVESTIGATION` when a new loop starts

The specific transition rules should be defined by your design, not inferred by the LLM.

This is the conceptual foundation for your LangGraph Director. Learn to model the transitions in plain Python first.

### B. Structured output and validation

The router should return something like:

```
class GameAction(BaseModel):    action: Literal[        "search_archive",        "talk_to_npc",        "cross_check",        "view_notebook",        "perform_ritual",    ]    target_id: str | None = None    query: str | None = None
```

The actual implementation should validate the action's parameters against the selected operation. For example, `talk_to_npc` requires a valid NPC ID, while `cross_check` requires two valid document IDs.

If the LLM produces invalid JSON, retry or ask the player to clarify. Do not execute an arbitrary action simply because the model returned it.

### C. Checkpoints versus long-term memory

This distinction is especially important for a time-loop game.

- Checkpoint: saves graph execution so an interrupted ritual can resume.
- Loop state: tracks what happened in the current attempt.
- Persistent Store or notebook: retains clues and selected consequences across loops.

You will need to define a reset function that initializes a new loop without erasing the notebook. Test that reset independently before integrating LangGraph persistence.

### D. Safe filesystem and Git operations

Your cursed repository is a game prop, but it uses real local Git operations. Treat that boundary as a security requirement.

- Create the repository and its local bare origin through a setup script.
- Hard-code the permitted repository root.
- Reject paths that resolve outside that root.
- Never accept a player-supplied path or remote URL for destructive operations.
- Use a local bare repository rather than a real GitHub remote.
- Test corruption, restoration, and full-loss operations in an isolated temporary environment first.

The game should never require a real GitHub token or a destructive operation against the player's actual repository.

## 7.1 Define contracts between components

Every component should have a clear input and output.

| Function               | Input                                    | Output                                 |
| ---------------------- | ---------------------------------------- | -------------------------------------- |
| `route_action()`       | Player's text and permitted actions      | Validated action candidate             |
| `search_documents()`   | Query and optional filters               | Document records with IDs and metadata |
| `cross_check()`        | Two document IDs                         | Structured consistency result          |
| `resolve_clues()`      | Action result and clue mapping           | Newly unlocked clue IDs                |
| `generate_npc_reply()` | NPC context and player question          | Dialogue text                          |
| `apply_action()`       | Game state and validated action          | Updated state and action result        |
| `evaluate_ritual()`    | Selected name and offering               | Win/loss verdict                       |
| `reset_loop()`         | Persistent player state and loss outcome | Fresh loop state                       |
| `apply_corruption()`   | Permitted corruption event               | Repository status and event result     |

You do not have to implement these exact function signatures, but each operation should have an explicit contract. This makes testing and replacement much easier.

## 7.2 Establish the most important invariants

These are conditions that must remain true regardless of which model responds or which tool is called.

- AP never becomes negative.
- A clue can only be unlocked by an authorized game event.
- The ritual verdict is determined by game rules, never by LLM judgment.
- A new loop resets temporary state but preserves designated persistent state.
- An NPC cannot retrieve secrets that its context or tools do not authorize.
- An interrupted action cannot accidentally charge AP twice when resumed.
- Cursed-repository operations cannot modify files or repositories outside the generated game area.
- If an LLM times out or produces invalid output, the game remains in a recoverable state.

The last two state-related invariants are particularly important. Test that an interrupted ritual resumes without repeating the action, and that a failed narration call does not undo a successfully committed game action.
